# Юридический полигон Harvey LAB

Задания открытого бенчмарка **Harvey LAB (Legal Agent Benchmark)** — `harveyai/harvey-labs`,
MIT — внутри DSH.OPEN.WEB: каталог из 2010 реальных юридических дел, документы дела,
рубрика проверки и оценка «всё-или-ничего» судьёй на DeepSeek.

## Зачем свой движок, а не оригинальный `lab-core`

Оригинальный движок — Python (`lab-core`, `>=3.12,<3.14`, `uv`, `pandoc`), а на машине
Python 3.14 и нет `uv`/`pandoc`; готового адаптера к DeepSeek в нём тоже нет. Поэтому
протокол бенчмарка повторён на Node внутри сервиса (`src/legalbench.mjs`), а данные
берутся из настоящего репозитория — задания, документы и рубрики не переписаны.

Что сохранено дословно:

- **формат задания**: `tasks/<практика>/<задание>[/<сценарий>]/task.json` + `documents/`;
- **рубрика**: критерии с `id`, `title`, `match_criteria`, `deliverables`;
- **правило оценки**: `1.0` только если пройдены **все** критерии, иначе `0.0`;
  эталонных ответов нет — судья проверяет наличие факта в работе;
- **единица работы**: файл-деливерабл с именем из задания.

## Данные на диске

| Путь | Что это |
| --- | --- |
| `data/legalbench/repo` | клон `harvey-labs` без блобов (blobless), только `task.json` + документы нужных заданий |
| `data/legalbench/catalog.json` | индекс: `id`, практика, тип работы, число критериев, теги |
| `data/legalbench/runs/<прогон>/` | `documents/`, `output/`, `instructions.md`, `criteria.json`, `scores.json`, `report.html` |

Клон «без блобов» экономит место: 2010 заданий занимают ~79 МБ вместо ~2.2 ГБ, потому что
содержимое документов подтягивается только для того задания, которое вы взяли
(`git sparse-checkout add tasks/<id>/**`).

## Командная строка

```powershell
node scripts/legalbench.mjs status                 # что скачано, сколько заданий
node scripts/legalbench.mjs sync [--refresh]       # собрать/обновить каталог (~80 МБ, нужен git)
node scripts/legalbench.mjs areas                  # практики: заданий и типичный размер рубрики
node scripts/legalbench.mjs list --area contracts --work-type draft --max-criteria 25 --limit 20
node scripts/legalbench.mjs show employment-labor/identify-issues-in-counterparty-motion-brief --criteria all
node scripts/legalbench.mjs prepare <id> --out data/legalbench/runs/demo
node scripts/legalbench.mjs grade --task <id> --output data/legalbench/runs/demo/output `
     --result data/legalbench/runs/demo --judge pro
node scripts/legalbench.mjs report --file data/legalbench/runs/demo/scores.json
```

`grade` возвращает код выхода 2, когда балл не 1.0 — удобно для скриптов и CI.

## Инструмент `legal_task`

То же самое внутри диалога, без терминала:

| Действие | Что делает |
| --- | --- |
| `status` | сколько заданий в каталоге и надо ли его скачивать |
| `sync` | скачать/обновить каталог |
| `list` | фильтры `area`, `work_type`, `query`, `max_criteria`, `limit` |
| `show` | инструкция заказчика, деливераблы, документы, первые критерии |
| `fetch` | подтянуть документы задания из git |
| `prepare` | создать папку прогона с `documents/` и `output/` |
| `grade` | проверить `output/` по рубрике и написать отчёт |

Инструмент описан в `src/tools.mjs` и подписан в интерфейсе как «Юридический полигон».
Навык `legal-agent-bench` объясняет модели порядок работы: выбрать задание с рубрикой до
~30 критериев, прочитать все документы, посчитать цифры самому, положить деливерабл с
точным именем в `output/`, прогнать `grade`, разобрать FAIL.

## Как ставится балл

Каждый критерий — отдельный вызов модели-судьи (`temperature: 0`, `max_tokens: 1200`).
В промпт попадают: название задания, `id` и `title` критерия, его `match_criteria`
(стандарт проверки) и текст деливераблов (до 24 000 символов на критерий). Судья обязан
ответить JSON `{"verdict": "PASS" | "FAIL", "reason": "…"}`. Разбор ответа терпимый:
принимаются `verdict`, `status`, `result`, `met`, `pass` и синонимы слов PASS/FAIL, в том
числе булевы значения и русские «выполнен / не выполнен», а причина берётся из `reason`,
`reasoning`, `explanation` и подобных полей. Если после этого вердикт так и не разобран,
делается одна повторная попытка с требованием строгого формата, а при пустом ответе
(рассуждение съело лимит вывода) запрос повторяется без усилия и с большим `max_tokens`.
Только после этого критерий считается FAIL — намеренно, чтобы «модель промолчала» не
превращалось в зачёт; сырой ответ в таком случае сохраняется в `scores.json` (поле `raw`).

Дальше действует правило бенчмарка: все PASS → `1.0`, иначе `0.0`. В `scores.json`
и `report.html` при этом видно и число пройденных критериев (например «22 из 23»), и
причину по каждому — балл 0.0 не означает «ничего не сделано».

## Стоимость

Один прогон = число критериев × один вызов судьи (деливерабл читается на каждый вызов,
но коротким фрагментом). Поэтому:

- `judge flash` — дешёвый и быстрый прогон, годится для отладки деливерабла;
- `judge pro` (`deepseek-v4-pro`, `effort: max`) — строгая проверка, для итогового балла;
- `--max-criteria N` проверяет только первые N критериев и **не** заменяет полный балл:
  в отчёте появляется пометка «Проверена часть рубрики (ограничение прогона) — итог
  «всё-или-ничего» относится к проверенному набору», рядом с баллом видно «пройдено N из M
  критериев», а в карточках — сколько критериев в рубрике всего. Защитный потолок на один
  прогон — 200 критериев (`DSHOW_LEGALBENCH_MAX_CRITERIA`);
- рубрики бывают большими: в `diligence` до 1114 критериев, у типовых дел 20–40.

Судья видит не весь деливерабл, а первые `DSHOW_LEGALBENCH_DOC_CHARS` символов и приписку
«текст обрезан». Для меморандума на 25 тысяч знаков действующего бюджета не хватает: хвост
документа судья не читает и честно ставит FAIL по критериям, которые разобраны в конце.
Поэтому важное — в начале, а длинную работу проверяют с поднятым бюджетом
(`DSHOW_LEGALBENCH_DOC_CHARS=40000`).

## Прогон-пример: как это выглядит на деле

Задание `employment-labor/identify-issues-in-counterparty-motion-brief` (возражение на
motion for partial summary judgment по WARN Act, рубрика 23 критерия, судья `pro`):

| Шаг | Что сделали | Итог |
| --- | --- | --- |
| 1 | первый меморандум, 18 абзацев | 14 из 23, балл 0.0 |
| 2 | добавили разборы по подсказкам судьи: цифры по Chattanooga, обрезанная цитата Voss, SUMF ¶ 14, декларация Briggs, mini-WARN Теннесси, прецедент Sixth Circuit | 20 из 23 |
| 3 | уточнили 60-дневную норму, обе версии арифметики ущерба, ссылки на Answer ¶ 24 и ¶ 33 | 22 из 23 |
| 4 | отдельный абзац про непоследовательность истца с faltering company + проверка с бюджетом 40 000 знаков | **23 из 23, балл 1.0** |

Расход на полный прогон — около 148 тысяч входных и 15 тысяч выходных токенов (деливерабл
перечитывается на каждый критерий). Отчёт того прогона лежит в
`data/legalbench/runs/demo-warn/report.html`, вердикты — в `scores.json` рядом.

## Переменные окружения

| Переменная | По умолчанию | Смысл |
| --- | --- | --- |
| `DSHOW_LEGALBENCH_DIR` | `data/legalbench` | где лежат клон, каталог и прогоны |
| `DSHOW_LEGALBENCH_REPO` | `https://github.com/harveyai/harvey-labs` | откуда брать задания |
| `DSHOW_LEGALBENCH_DOC_CHARS` | `24000` | сколько символов деливерабла видит судья на критерий |
| `DSHOW_LEGALBENCH_MAX_CRITERIA` | `200` | предохранитель на один прогон |

## Ограничения, о которых надо знать

- Материалы и рубрики — англоязычные и про право США (WARN Act, UCC, Delaware). Это
  тренажёр и проверка качества работы, а не источник российских правовых норм.
- Практика `firm-knowledge` ссылается на общий корпус `dms/` на гигабайты, а локальных
  документов у таких заданий нет: без корпуса задание не решается по существу.
- Судья — модель. Вердикт на границе формулировок бывает спорным: полезнее смотреть на
  `reason`, а не только на PASS/FAIL, и перечитывать `match_criteria`.
- Задание «пройдено» не значит, что меморандум хорош: рубрика проверяет набор фактов,
  а не стиль и не юридическую стратегию целиком.

## Проверка

```powershell
npm run test:legalbench    # node --test test/legalbench.mjs
```

Тесты идут без сети и без git: разбор `id` (в том числе запрет выхода за `tasks/`),
фильтры каталога, разбор вердикта судьи (JSON, JSON в тексте, слова, мусор), сборка
промпта судьи, чтение деливераблов и отметка отсутствующих, правило «всё-или-ничего»,
отчёт с экранированием, честное «каталог не скачан».
