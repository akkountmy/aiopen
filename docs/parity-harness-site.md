# Харнесс против DSH open web: что сравнили, что добавили, чем проверили

Дата: 2026-11-04. Сравнение локального харнесса DSH и сервиса DSH open web
(`https://dshopen-vladimir00177.msk1.amvera.tech`), итог аудита и запас прочности
сервиса под 50 одновременных пользователей.

## 1. Навыки: паритет закрыт

На сайте 49 навыков (`/api/health` → `skills:49`, ровно столько папок в
`skills/`). В харнессе те же навыки плюс четыре, которые описывают сам харнесс и
на сервере бессмысленны:

| Навык харнесса | Почему не переносим |
|---|---|
| `cordis-plugin-development` | про динамические Cordis-плагины процесса DSH; у сайта такого слоя нет |
| `editing-cordis-compositions` | про `cordis.yml` и пресеты — только локальный харнесс |
| `security-review` | опирается на инструменты `security_audit` / `security_redact_*`, которых на сайте нет |
| `thread` | контракт памяти сессий Thread — серверная особенность DSH |

Обратная разница: у сайта есть `material-intake` (приём и разбор материалов),
которого нет в харнессе. 18 файлов `SKILL.md` отличаются текстом осознанно —
это адаптация под инструменты сайта; копировать харнессные версии поверх нельзя,
иначе навык начнёт ссылаться на несуществующие инструменты.

Добавлено в этом цикле: `canvas-diagram` (редактируемые диаграммы в интерфейсе).

Каталог навыков в системном запросе — по строке на навык, 10 841 знак на 49
навыков. Раньше описание резалось по 240 знакам и теряло слова-триггеры в конце
фразы; теперь тема берётся до первого тире, а остаток строки занимают триггеры в
кавычках. Замер: было 34 потерянных триггера в 9 навыках, стало 4 в 3
(`interior-design`, `obscura`, `ploy-site` — хвост длинного перечисления),
проверяется `test/catalog.mjs`.

## 2. Возможности: что есть у харнесса и отсутствовало на сайте

| Возможность харнесса | На сайте |
|---|---|
| `memory_search` / `memory_write` | инструмент `remember` + автоматический отбор фактов в промпт (`searchFacts`, до 28 фактов по теме сообщения) — эквивалент есть, отдельный поиск не нужен |
| `subagent`, `workflow` | `spawn_agent` (параллельные агенты) |
| `word_*`, `excel_*`, `ppt_*`, `read_image` | `create_word` / `create_excel` / `create_pptx` / `create_pdf`, `read_document`, `analyze_image` |
| `browser_*`, `web_fetch` | `read_page`, `check_page`, `scrape_page`, `fetch_url`, `fetch_many`, `crawl` + браузер Obscura и встроенный Chromium |
| `todo_write` | состояние задачи и шаги выполнения (`taskstate.mjs`, раздел выполнения в интерфейсе) |
| `diagram_create` | навык `canvas-diagram` (без инструмента, диаграмма строится в интерфейсе) |

Вывод: применимых возможностей, которых нет на сайте, не осталось.

## 3. Что исправлено аудитом

| Находка | Риск при 50 пользователях | Исправление |
|---|---|---|
| `run_js` выполнялся в основном процессе | один `while(true)` вешал сервис всем | `worker_threads` с лимитом памяти 384 МБ, принудительное завершение по таймауту |
| не было общего предела одновременных задач | 50 контекстов в памяти, OOM | счётчик на сервис (10), на аккаунт (3), очередь 60 с, `429`/`503` с `Retry-After` |
| вызов модели без таймаута | зависший запрос держал место до перезапуска | потолок 300 с, 3 повтора с нарастающей паузой, `504` |
| сторож задачи получал абсолютное время вместо задержки | Node ставил 1 мс → каждая задача обрывалась сразу | `left = max(1000, deadline - now)` |
| тяжёлые инструменты (Chromium, Python, распаковка, анти-бот) не считались | три пользователя выедали CPU всем | общий семафор на 3 места, убийство всего дерева процессов |
| у инструмента не было предела работы | один инструмент занимал место 45 минут | дедлайн 120 с (`DSHOW_TOOL_DEADLINE_S`) с понятной ошибкой |
| `index.json` писался целиком на каждое сообщение | на 17 МБ это ~0.8 с блокировки цикла на сообщение | отложенная запись 2.5 с для больших файлов, маленькие — сразу |
| распознанный текст вложения лежал в индексе | один PDF на 150 тыс. знаков раздувал общий файл состояния | в индексе 2 000 знаков, полный текст в `<DATA_DIR>/attach/<id>.txt` |
| запись индекса с откатом в неатомарную | обрыв = битый `index.json` | только атомарная замена, `fsync`, при ошибке — исключение |
| `SIGTERM` оставлял процесс без порта | облако убивало контейнер, недописанный индекс | `closeIdleConnections`, принудительное закрытие через 3 с, `process.exit` |
| удаление диалога не убирало файлы вложений | папка данных растёт годами | вместе с диалогом удаляются записи и файлы |
| проверка ответа считала выдумкой числа, которые назвал сам пользователь | 86 «серьёзных находок» на 87 ответов за неделю, 21% ответов переписывались зря | числа из запроса и расчёт из имеющихся стали опорой (`buildSupport`, `derivedSeen`), проверяющий модель получил тот же блок |
| файл, созданный в прошлом ходу, считался обещанием несуществующего | 12 ложных находок за неделю | в проверку передаётся список файлов проекта (`listTree`, глубина 3) |
| каталог навыков резал описание по 240 знакам вместе со словами-триггерами | 34 триггера в 9 навыках не доходили до модели — навык не вызывался по своим словам | `compactDescription`: тема до тире + триггеры в кавычках, потеря 4 триггеров в 3 навыках (хвост списка) |
| шаг `use_skill` в ленте показывал «Навык» без названия | не видно, сработал ли навык, разбор качества слеп | `toolSummary` отдаёт id навыка и путь проверенного файла |
| память не ограничивалась ничем, кроме OOM-убийцы | один прогон с браузером и Python ронял контейнер вместе с чужими ответами | потолок `DSHOW_MAX_RSS_MB` = 1536: выше него новые задачи и тяжёлые инструменты не начинаются, отказ `503` с `Retry-After` |

## 4. Пределы нагрузки

Все числа — переменные окружения, `0` означает «без предела».

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `DSHOW_MAX_RUNS` | 24 | одновременных задач на сервис |
| `DSHOW_RUNS_PER_USER` | 3 | одновременных задач на аккаунт |
| `DSHOW_RUN_WAIT_S` | 60 | сколько задача ждёт свободного места |
| `DSHOW_MAX_WAITING_RUNS` | 120 | длина очереди ожидания |
| `DSHOW_RUN_MAX_MIN` | 45 | потолок времени задачи |
| `DSHOW_MODEL_TIMEOUT_S` | 300 | потолок одного обращения к модели |
| `DSHOW_MESSAGES_PER_10MIN` | 60 | сообщений на аккаунт за 10 минут |
| `DSHOW_HEAVY_TOOLS` | 3 | одновременных тяжёлых инструментов |
| `DSHOW_TOOL_DEADLINE_S` | 120 | потолок работы одного инструмента |
| `DSHOW_CRAWL_CONCURRENCY` | 2 | одновременных загрузок при обходе сайта |
| `DSHOW_FETCH_TIMEOUT_S` | 30 | таймаут загрузки страницы |
| `DSHOW_MAX_ATTACHMENT_MB` | 64 | размер вложения |
| `DSHOW_MAX_PARSE_MB` | 24 | размер документа для разбора |
| `DSHOW_MIN_FREE_MB` | 256 | ниже этого свободного места записи запрещаются |
| `DSHOW_MAX_RSS_MB` | 75 % ОЗУ контейнера, не больше 1536 | потолок памяти процесса: выше него новые задачи не начинаются |
| `DSHOW_WATCHDOG_S` | 180 | сторож зависания: столько секунд стоящей очереди событий — и процесс перезапускается сам |
| `DSHOW_AUTO_RESUME` | 1 | `0` — не продолжать прерванные задачи при старте (нужно при разборе зависания) |

Состояние видно в `/api/health` → блок `load`:

```json
{"runs":{"active":0,"waiting":0,"limit":24,"waitMs":60000,"maxWaiting":120,"rejected":0,"waited":0},
 "memory":{"rssMb":170.5,"heapUsedMb":77.1,"externalMb":5.6},
 "loopLagMs":1,"activeRuns":0,
 "watchdog":{"enabled":true,"blockedMs":0,"intervalMs":5000,"hangMs":180000,"beatMs":60000},
  "limits":{"maxRuns":24,"runsPerUser":3,"runMaxMinutes":45,"modelTimeoutSeconds":300,
            "maxRssMb":376,"maxWaitingRuns":120,"rssMb":170.5,
            "containerMemoryMb":500,"containerCpuCores":0.25}}
```

Разбор зависания 4 ноября: сервис перестал отвечать на `/api/health` и не
восстановился сам, при этом статус контейнера остался RUNNING, а в журнале не
было ни строки об отказе — последняя запись 14:36:04, дальше тишина на двадцать
минут. Перезапуск помог, но при следующей загрузке сервис автоматически
продолжил ту же задачу и завис снова. С `DSHOW_AUTO_RESUME=0` поднялся сразу.
Вывод, который в коде: тишина в журнале — такая же авария, как исключение,
поэтому теперь есть `[beat]` раз в минуту и сторож, который перезапускает
процесс после трёх минут стоящей очереди событий (`DSHOW_WATCHDOG_S`), а не
оставляет его молча висеть.

## 5. Чем проверено

- `node scripts/check.mjs`: **54 из 54 прошли, 0 упали** (35 тестов требуют `--live`).
- `test/load.mjs` — 50 одновременных диалогов у 5 аккаунтов с заглушкой модели:
  **41 выполнена, 2 × 503, 7 × 429**, все отказы с `Retry-After`; пик обращений к
  модели ровно **4** (предел соблюдён), отставание цикла событий **25 мс**,
  память **215 → 234 МБ**, после наплыва активных задач 0, сервис снова принимает
  работу, в журнале нет необработанных отказов.
- `test/attach-text.mjs` — 13 проверок выноса текста вложений (короткий остаётся
  в индексе, длинный уходит в файл, чтение собирает полный текст, удаление
  убирает файл).
- `test/review-support.mjs` — 6 проверок опоры для ревью: числа из запроса и
  расчёт из имеющихся не считаются выдумкой, а число без происхождения —
  считается; файл из прошлого хода не ловится как обещание.
- `test/catalog.mjs` — 6 проверок каталога навыков: предел строки, отсутствие
  обрыва на служебном слове, сохранность триггеров, бюджет каталога, потолок
  тела навыка.
- `test/capacity-memory.mjs` — 6 проверок потолка памяти: давление считается,
  `0` выключает проверку, тяжёлый инструмент не стартует на пределе и не течёт
  местом в счётчике.
- `scripts/skill-matrix.mjs` — 12 живых запросов по навыкам (Word, Excel, PDF,
  презентация, сайт, данные, ресёрч, юрзадача, смета, аудит, инцидент, схема):
  смотрит, открыла ли модель навык, тот ли самый, вызвала ли инструменты из
  инструкции и проверила ли результат.
- Прод после выкладки: `/api/health` → `skills: 49`, `loopLagMs: 1`,
  `rssMb: 170.5`; главная — 200; в журнале запуска нет строк об ошибках;
  залитые файлы совпадают с локальными по размеру байт в байт.

## 6. Что осталось нерешённым осознанно

- **Горизонтального масштабирования нет.** Состояние и очередь живут в одном
  процессе, на Amvera включён `run.singleton`. Вторая копия увидела бы чужие
  задачи только после выноса очереди и состояния наружу (Redis/БД). До 50
  человек это не нужно и стоит дороже, чем польза.
- **Память модели общая.** Предел `DSHOW_MAX_RUNS` считает задачи, а не токены:
  стоимость ограничивается отдельными пределами на задачу
  (`DSHOW_TASK_LIMIT_USD`, `DSHOW_TASK_STEP_USD`).
- **Запас по железу.** 50 человек при 10 одновременных задачах: 170–235 МБ RSS,
  отставание цикла 1–25 мс. Рекомендация — 2 ГБ памяти и 2 vCPU; при росте до
  100 человек поднимать `DSHOW_MAX_RUNS` нельзя без выноса состояния наружу.
