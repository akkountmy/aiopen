# Промпт аудита: харнесс DSH + сервис DSH.OPEN.WEB

Готовый к вставке промпт. Запускать в локальном харнессе (DSH Web GUI, `http://127.0.0.1:3080`),
новая сессия, модель `deepseek-flash`, усилие `high`. В сервисе DSH.OPEN.WEB применимы только
проверки C2, D1, E — у него нет ни `cordis_inspect_query`, ни `pwsh` по локальным путям.

## Текст промпта (копировать ниже линии)

---

Ты — аудитор двух систем: локального харнесса DSH (профиль `web`, `C:\Users\33620\.dsh`) и
сервиса DSH.OPEN.WEB (`D:\DSHarness-0.1\DSH.OPEN.WEB`). Цель — найти и обосновать: дубли
возможностей, места зацикливания, лишний постоянный расход токенов, случаи, когда навык или
плагин подключён не по делу. Качество выполнения задач при этом не должно упасть.

Работа в две фазы. **Фаза A — только аудит и отчёт, без правок.** Фаза B — правки, и только
после моего явного «делай» по конкретному списку.

### 2. Дисциплина расхода (аудит сам не должен жечь токены)

- Файл больше 30 КБ целиком не читать: `grep` по ключу, потом `read` с `offset`/`limit`.
- Никакого `web_search` и внешних загрузок, кроме одного запроса `/api/health` сервиса.
- Субагент — максимум один, и только если ветка проверок независима; у него в промпте те же
  лимиты и требование вернуть числа, а не текст.
- Один и тот же файл не читать дважды: нужные числа выписывай в рабочий блокнот отчёта.
- Любую «оптимизацию» без замера до и после не предлагать.
- Догадка, которую нечем доказать, помечается `не проверено` — не выдаётся за находку.

### 3. Проверки

**A. Дубли**

1. Структурные: подтвердить `duplicates: 0` и что каждый бандл из `dsh.profile.bundles` либо
   даёт инструменты, либо честно выключен; ORPHAN-строк в патче быть не должно.
2. Функциональные: взять `listTools` и составить таблицу «задача → инструменты, которые её
   решают». Искать пары на одну задачу:
   - документы: `word_*` / `excel_*` / `ppt_*` против навыков `office-docx` / `office-xlsx` / `office-pptx`;
   - веб: `web_fetch` / `web_search` против навыков `deepseek-search`, `web-scraping`, `obscura`
     и против `browser_*` (18 инструментов);
   - диаграммы: `diagram_create` против навыков `canvas-diagram`, `answer-visuals`;
   - память: `memory_search` / `memory_write` против `query_session_memory` / `record_decision`;
   - оркестрация: `subagent` / `subagent_fork` / `workflow` / `ralph` против навыка
     `agent-orchestration` и пресета `expert-orchestrator`.
   Для каждой пары — вердикт: один путь основной, второй оставить как резерв (и тогда убрать
   его из описаний, где он конкурирует), либо честно два разных назначения с правилом выбора.
3. Копии контента: два дерева навыков (харнесс и репозиторий сервиса) живут раздельно, 18 файлов
   уже разошлись. Решение оформить как правило: один источник истины + скрипт синхронизации,
   либо явное «это две версии, менять обе». Без решения расхождение будет расти.
4. Деплой: репозиторий 46 навыков, живой сервис отдаёт 45 — найти, что не доехало.
5. Память: три хранилища (плагин `dsh-memory`, `dsh-thread`, `src/memory.mjs` сервиса) — проверить,
   не пишется ли один факт в два места и не попадает ли он в промпт дважды.

**B. Зацикливания**

1. Харнесс: найти, есть ли предел шагов/бюджет вызова. Если нет — это находка P0 с предложением
   конкретного числа (по умолчанию 40 шагов на задачу, как в сервисе) и места, куда его писать.
2. Проверить, что предохранители работают, а не просто объявлены: `model-split`
   (`budgetCalls: 60`, бюджет токенов вывода), `dsh-trim`, `dsh-messages-sanitizer`,
   `dsh-model-health`. Для `model-split` — тест: заведомо больше вызовов, чем бюджет, и отказ
   должен прийти до конца бюджета.
3. Сервис: `CONTEXT.maxSteps = 40` × 24 отрезка = 960 шагов на задачу; `budget.limitUsd`
   в `src/agent.mjs`; `SUBAGENT_MAX_DEPTH = 1`, `SUBAGENT_MAX_TASKS = 4`. Проверить по коду, что
   при `budgetHit` и на `stepLimit` цикл реально останавливается и отдаёт итог, а не уходит в
   следующий отрезок молча.
4. Эмпирика по харнессу: в `~/.dsh/sessions` найти подряд идущие вызовы одного инструмента с
   одинаковыми аргументами. Больше трёх одинаковых подряд — зацикливание, выписать сессию,
   инструмент, аргументы.
5. Экономический тест: один и тот же запрос средней сложности три раза на дешёвой модели;
   фиксировать шаги, вход/выход токенов, время. Разброс больше 2× — искать причину.

**C. Токены**

1. Постоянная часть харнесса: суммарный размер схем всех инструментов (знаков), каталог навыков,
   блоки памяти и правил. Перевести в токены (русский текст ≈ знаки/3, латиница ≈ знаки/4) и
   показать, сколько из этого не используется никогда.
2. Сервис: фактический `systemPrompt()` на типичном входе против `PROMPT_BUDGET.limitChars = 19500`.
   Отдельно — 11 536 знаков каталога навыков: это ~3,5–4 тыс. токенов на каждый запрос, даже когда
   навык не открывается.
3. Реальные траты: по логам/файлам сессий — топ-10 самых дорогих сессий, причина по каждой
   (необрезанный результат инструмента, повторное чтение одного файла, полный дамп файла,
   лишние открытия навыков).
4. Предложить целевые числа и защиту: постоянная часть ≤ 12 тыс. токенов на систему; рутинный ход
   ≤ 40 тыс. входных токенов; предупреждение в лог при превышении (как `PROMPT_BUDGET` в сервисе).

**D. Ленивая загрузка**

1. Навыки: описание в каталоге не должно дублировать тело и должно быть ≤ 230 знаков; в
   `SKILL.md` только `name` и `description` в frontmatter. Найти навыки с пересекающимися
   триггерами (два навыка открываются на одну формулировку) — это гарантированная лишняя загрузка.
2. Плагины: для каждого из 33 пакетов — сколько инструментов/сервисов он даёт в сессии. Отдельно
   найти те, что дают 0 или дублируют ядро. Проверить, что выключение `aginxbrowser` действительно
   сняло 15 нерабочих схем (в `listTools` не должно быть `agx_*`).
3. Сформулировать правило на будущее: инструмент попадает в промпт только если у него есть
   задача, которую не решает уже подключённый; выключенный пакет не должен оставлять схем.

**E. Качество (проверять последним, чтобы отличить реальную пользу от экономии)**

1. Пять коротких эталонных задач на обеих системах: документ `.docx`, книга `.xlsx`, поиск в
   интернете с источником, разбор файла-выгрузки, обычный ответ с таблицей.
2. Метрики по каждой: выполнено/нет, шагов, входных и выходных токенов, деньги, время.
3. Приёмка — по `docs/parity-service-vs-harness.md` и `npm test` сервиса.
4. Правило: если предложенная экономия ломает хотя бы один эталонный кейс — она не принимается.
   Экономия без сохранения качества считается регрессом.

### 4. Формат результата

Файл `docs/audit-2026-11-03.md` и короткая сводка в чат.

Сводка: 8–12 строк — сколько находок по классам, худшая находка, ожидаемая экономия токенов,
что требует моего решения.

Файл: таблица находок, каждая строка — `P0/P1/P2 · класс · симптом · доказательство (команда или
файл:строка) · причина · минимальная правка · ожидаемая экономия · риск`. P0 — то, что прямо
сейчас жжёт токены или может зациклиться; P1 — дубли, из-за которых правки расходятся; P2 —
гигиена. Больше 25 находок не перечислять: лишнее слить по классам.

В конце файла — блок `Что НЕ проверял и почему` и `Что предлагаю делать в фазу B` (максимум пять
P0, каждая правка атомарная, с точкой отката: для харнесса — копия файла в `~/.dsh`, для сервиса —
`git diff` до и после).

### 5. Запреты

- Не править ничего в фазе A, в том числе «очевидное».
- Не трогать поставленный с деплоем каталог `agent-presets`: пресеты живут в `~/.dsh/.agent-presets`.
- Перед правкой любой строки `cordis.patch.yml` — загрузить навык `editing-cordis-compositions`.
- Не перезапускать `dsh web` и не деплоить сервис: изменения, требующие перезапуска, выносить
  отдельным пунктом «нужен перезапуск».
- Не править навык только в одной копии, если решение из A3 не принято.
- Не удалять ничего, что не доказано как лишнее: сомнительное — в «кандидаты», не в удаление.

### 6. Критерий «готово»

Фаза A готова, когда по каждому из пяти классов есть либо находка с доказательством, либо строка
`нарушений не найдено` с командой, которой это проверено. Отчёт без чисел и без путей не
принимается: «выглядит нормально» — не результат.

## Как этим пользоваться

1. Вставить текст между линиями в новую сессию харнесса.
2. Ответ фазы A сохранить в `docs/audit-2026-11-03.md` (путь в промпте можно менять под дату).
3. По каждой P0 решить отдельно: «делай» / «не надо». Только после этого — фаза B.
