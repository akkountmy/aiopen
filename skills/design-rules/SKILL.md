# Правила дизайна: превратить правку в правило

Пользователь говорит «нет, тени полупрозрачные, а не рамка». Через неделю
другая страница снова с рамкой. Причина не в памяти модели, а в том, что правка
осталась в чате. Этот навык переносит её в проект — так, чтобы следующая
страница её уже соблюдала.

## Пять правил, которые нельзя нарушать

1. **Только вкус пользователя.** Правило — это то, что он сказал или выбрал.
   Свои догадки о «хорошем дизайне» в DESIGN.md не попадают.
2. **Не выдумывать причину.** Если он сказал «убери рамку», а не почему, —
   причина либо спрашивается одним вопросом, либо помечается как гипотеза.
   Придуманное «почему» через месяц защищает не то решение.
3. **Сначала предложить — потом стоп.** Ничего не записывать в DESIGN.md без
   подтверждения. Показать список правил и ждать.
4. **Проверка сильнее фразы.** Правило, которое можно поймать механически
   (`find_in_files` по цвету, запрет значения, пункт в чек-листе), работает
   надёжнее, чем абзац прозы.
5. **Писать для агента, которого здесь нет.** Формулировка должна быть понятна
   без этой переписки: что делать, где, и как убедиться.

## Шаг 1. Собрать сигналы

Правка вкуса — не только слово «нет». Сигналы, которые считаются:

| Сигнал | Пример |
| --- | --- |
| Явный запрет | «никаких градиентных кнопок», «без эмодзи» |
| Повторная правка | третий раз меняет тот же отступ или вес шрифта |
| Выбор из вариантов | из трёх обложек выбрал самую спокойную |
| Ссылка на другой продукт | «как в Linear», «не как у всех этих лендингов» |
| Оценка «слишком» | «слишком пёстро», «слишком много воздуха», «дёшево» |

Всё остальное — баг, опечатка, содержание задачи — правилом не становится.
Правка в одном месте, о которой он не говорил обобщённо, — тоже: сначала
спросить, «это правило на весь проект или только здесь».

## Шаг 2. Отсеять одноразовое

Одноразовое: конкретный текст, конкретная картинка, временная заглушка,
ошибка вёрстки, «здесь не влезло». Правило из этого не выводится.

Класс: «тени», «радиусы», «как показываем числа», «что делаем с пустым
состоянием», «какой шрифт для заголовков». Если правка повторится на любой
следующей странице — это класс.

## Шаг 3. Выбрать уровень

| Уровень | Как выглядит | Когда |
| --- | --- | --- |
| Точка | «на карточках тарифов радиус 20 px» | одно место, редко |
| Класс | «радиусы: 8 для полей, 16 для карточек, 24 для модалок» | обычный случай |
| Всеобщее | «никаких чистых чёрных и белых фонов, только оттенки базы» | принцип, редко |

По умолчанию — класс: он переносится на новые экраны, но не превращается в
лозунг, который потом некуда применить. Всеобщее правило пишется, только если
пользователь сам сформулировал принцип.

## Шаг 4. Куда записать

Один файл `DESIGN.md` в корне проекта, разделы фиксированные:

- **Surfaces** — фоны, слои, границы, тени, радиусы;
- **Color** — палитра, роли, состояния, тёмная тема;
- **Typography** — семейства, шкала размеров, веса, трекинг, интерлиньяж;
- **Spacing & layout** — шкала отступов, сетка, максимальные ширины, брейкпоинты;
- **Motion** — длительности, кривые, что анимируется и что нет;
- **Interaction** — состояния контролов, фокус, обратная связь;
- **Copy** — тон, обращение, заголовки, ошибки.

Формат записи — правило, затем причина, затем цитата пользователя с датой:

```markdown
- Тени полупрозрачные и мягкие, без рамки вокруг карточек. Карточка и рамка
  одновременно читаются как два разных слоя.
  <!-- 2026-11-24: «рамка делает вид дешёвым, оставь только тень» -->
```

Нет раздела — создать. Есть файл, но нет раздела — дописать в конец, не
переписывать чужое.

## Шаг 5. Проверка вместо обещания

К каждому правилу, где это возможно, — механическая проверка:

- запрещённый цвет или значение — `find_in_files` по проекту;
- «все отступы из шкалы» — сверить вычисленные значения на отрендеренной
  странице (`check_page`), а не глазами по CSS;
- «пустое состояние объясняет следующий шаг» — пункт в чек-листе сдачи
  страницы;
- «нет анимации на частых действиях» — проверка по навыку `motion`.

Если проверку придумать нельзя — так и написать: «проверяется взглядом на
отрендеренной странице». Ложная проверка хуже её отсутствия.

## Шаг 6. Отчёт и стоп

Показать таблицей, ничего не записывая:

| # | Наблюдение | Правило | Уровень | Куда | Проверка |
| --- | --- | --- | --- | --- | --- |
| 1 | «рамка выглядит дёшево» | карточки без рамки, только мягкая тень | класс | Surfaces | `find_in_files` по `border:` в карточках |

Под таблицей — что осталось неясным: причина не названа, уровень спорный,
правило противоречит уже записанному. Противоречие решается заменой старой
записи, а не двумя правилами рядом.

Дальше — ждать. После «да» записать в `DESIGN.md` через `write_file`
(существующий файл предварительно прочитать `read_file`, чтобы не потерять
чужие разделы) и назвать, сколько правил добавлено.

## Когда записывать нечего

Сказать прямо одной строкой: «правок вкуса в этой сессии не было — правило не
записываю». Пустой `DESIGN.md` с десятью выдуманными принципами хуже, чем
отсутствие файла: следующая страница будет соблюдать не то.

## Если правок накопилось много

Сначала записать те, где пользователь назвал причину сам. Правила-гипотезы
(причина не названа) — отдельным блоком «предположения, требуют подтверждения»,
чтобы через месяц было видно, что это догадка, а не его слова.
