# Постановка задачи аналитике

Аналитика — не «дай данные», а ответ на решение. Задача без решения, метрики и базы сравнения возвращается красивой таблицей, которую никто не использует.

Правило: сначала формулируется решение, которое примут по результату, потом вопрос, потом метрика. Обратный порядок даёт отчёт, который невозможно оспорить, потому что непонятно, что он доказывает.

## Бриф: обязательные поля

| Поле | Что должно быть | Пример провала |
|---|---|---|
| Решение | Что сделаем по итогу | «посмотрим» |
| Вопрос | Один, проверяемый | «как дела с продажами» |
| Метрика | Определение и формула | «конверсия» без числителя и знаменателя |
| Разрез | Сегмент, канал, период | «в целом по всем» |
| База сравнения | Период, план, прошлый год, контрольная группа | «сравним с прошлым» без дат |
| Источник | Система и таблица, а не «из базы» | «выгрузи из CRM» |
| Формат | Таблица, файл, дашборд, дата обновления | «пришли отчёт» |
| Срок и приёмка | Дата и критерий готовности | «надо вчера» |

Шаблон брифа — `template.md` рядом с навыком.

## Словарь метрик

Каждая метрика описывается один раз и дальше используется без «уточнений на ходу»:

| Элемент | Пример |
|---|---|
| Название и версия | Одобрение заявки, v3 |
| Числитель | Число выданных заявок за период |
| Знаменатель | Число рассмотренных заявок за тот же период |
| Исключения | Тестовые, дубли, отозванные клиентом, отказ по технической ошибке |
| Источник | Система заявок, таблица заявок, поле даты решения |
| Владелец | Владелец процесса кредитования |
| Обновление | Ежедневно, до 06:00 |
| Известные искажения | Заявки, поданные повторно одним клиентом, считаются дважды |

Без исключений и владельца метрика через месяц начнёт считаться иначе, и сравнение с прошлым периодом станет ложью.

## Проверка данных до расчёта

1. Сходимость с источником: сумма по выгрузке = сумма в системе или отчётности за тот же период.
2. Дубли: по ключу заявки, по клиенту, по операции.
3. Пропуски: доля пустых по каждому важному полю; пустое не заполняется средним без пометки.
4. Границы периода: что попадает в последний день, в каком часовом поясе, как учтены операции на стыке.
5. Типы: числа не как текст, даты в одном формате, разделитель десятичной части.
6. Свежесть: до какой даты данные полные, где ещё не догрузились.

Не прошла проверка — результат не публикуется, а возвращается вопрос о данных. Иначе метрика живёт в отчёте и путает решения.

## A/B-тест

| Элемент | Как формулировать |
|---|---|
| Гипотеза | Изменение X повысит метрику Y на Z, потому что механизм такой-то |
| Основная метрика | Одна, заранее; остальные — вторичные |
| Guardrail | Что не должно ухудшиться (отток, доля дефолтов, стоимость фондирования) |
| Минимальный эффект (MDE) | Меньший эффект не оправдает внедрение |
| Объём выборки | На группу примерно `16 × σ² / Δ²` при alpha 0,05 и мощности 80% |
| Длительность | Не меньше полного цикла (неделя или месяц продукта), без остановки «на пике» |
| Анализ | Сравнение средних или долей с интервалом, а не «стало больше» |

Ломает тест чаще всего: подглядывание и остановка по первому значимому результату, смена метрики по ходу, сезонность без контрольной группы, эффект новизны у активной аудитории, десяток метрик без поправки на множественные сравнения.

Если выборки не хватает, честный вывод — «эффект меньше MDE, данных мало для решения», а не «тренд положительный».

## Как принять работу аналитика

1. Открыть одну цифру и пересчитать вручную по исходным данным — это проверка на порядок величины.
2. Проверить сумму частей: доли по сегментам складываются в целое, суммы по месяцам — в итог.
3. Посмотреть знаменатель: не изменился ли он между периодами (главная причина ложного роста).
4. Проверить фильтры: тестовые, дубли, отмены, границы периода.
5. Спросить запрос: если расчёт нельзя повторить, его нельзя и защитить.
6. Сверить с отчётностью или соседним отчётом; расхождение — повод разобраться, а не «у аналитика свои данные».
7. Проверить сравнение: одинаковые периоды, одинаковые определения, одинаковые валюты и масштабы.

Средние отношения считаются от агрегатов: `сумма(плохих) / сумма(всех)`, а не среднее по средним — иначе мелкий сегмент весит как крупный.

## Дашборд

- Один экран — одно решение, а не «всё про бизнес».
- Для каждой метрики: значение, сравнение с базой, тренд, разрез — иначе цифра не читается.
- 6–8 плиток максимум; остальное уходит во второй экран.
- Владелец, частота обновления и определение метрики подписаны рядом.
- Ошибка в данных видна явно: «нет данных» вместо нуля.

## Чек-лист перед отправкой задачи

1. Названо решение, которое примут по результату.
2. Метрика определена формулой, с исключениями и источником.
3. Разрез и база сравнения заданы датами, а не словами.
4. Формат, срок и критерий приёмки зафиксированы.
5. Для теста есть основная метрика, guardrail и MDE.
6. Для дашборда есть список решений, которые он поддерживает.
