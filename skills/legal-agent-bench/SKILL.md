# Юридический полигон: пройти задание Harvey LAB и получить балл

## Когда открывать
«Возьми задание из Harvey LAB», «проверься на юридическом бенчмарке», «нужно
дело на анализ / драфт / ревью контракта», «прогони меня по рубрике», «сколько
критериев я закрыл». Полигон — не генератор документов: он даёт **реальное
дело с настоящими материалами и рубрикой**, а балл ставит отдельный судья.

Что это НЕ такое: не справочник по праву США и не замена профильным навыкам
(`house-build-*`, `office-docx`). Материалы дел англоязычные, право —
американское (WARN Act, UCC, Delaware), поэтому российские нормы туда не
подставлять.

## Что уже есть — не изобретать заново
| Что | Чем брать |
| --- | --- |
| Каталог 2010 заданий, 27 практик | `legal_task` с `action="status"` / `"list"` |
| Полный текст задания, рубрика, список документов | `action="show"` (rubric печатается по 6 критериев) |
| Скачать документы дела и создать папку прогона | `action="prepare"` |
| Оценка по рубрике с отчётом | `action="grade"` |
| То же из терминала, без диалога | `node scripts/legalbench.mjs …` |

Данные и прогоны лежат в `data/legalbench/`: `repo/` — клон
`harveyai/harvey-labs` (без блобов), `catalog.json` — индекс, `runs/` — прогоны.

## Порядок работы — не переставлять
1. **Выбор задания.** `action="list"` с `area`, `work_type`, `query`,
   `max_criteria`. Для первого прогона брать рубрику до ~30 критериев: полный
   балл требует закрыть все, а каждый критерий — отдельный вызов судьи.
2. **Чтение задания.** `action="show"` — инструкция заказчика, файлы-деливераблы,
   рубрика. Рубрика не секрет: по ней видно, какие факты обязаны появиться.
3. **Подготовка.** `action="prepare"` копирует документы дела и создаёт
   `output/`. Первый `prepare` незнакомого задания тянет его документы из git
   (десятки секунд) — это нормально.
4. **Работа с материалами.** Читать все документы дела, а не первый: рубрика
   почти всегда проверяет цифры, цитаты и расхождения между документами.
   Считать арифметику самому — ошибки в расчётах истца и есть частая зацепка.
5. **Деливерабл.** Файл с точным именем из задания — в папку `output/`
   (`create_word`, `write_file`). Имя не совпало — судья нечего проверять.
6. **Оценка.** `action="grade"` с `dir` прогона. Судья возвращает по каждому
   критерию PASS/FAIL и причину; отчёт — `report.html` рядом со `scores.json`.
7. **Разбор.** FAIL — это список конкретных фактов, которых не хватило.
   Дописывать деливерабл и запускать `grade` повторно можно сколько нужно.

## Как читать результат
- **Балл 1.0 или 0.0**, третьего нет: пройдены все критерии или нет. 22 из 23 —
  это 0.0, и это честно: так работает оригинальный LAB.
- **PASS/FAIL по критерию ставит модель-судья**, а не человек. Вердикт бывает
  спорным на границе формулировок; при сомнении перечитать `match_criteria` и
  убедиться, что деливерабл проговаривает факт прямым текстом, а не намекает.
- **Стоимость.** Один прогон = число критериев × вызов судьи. `criteria_limit`
  ограничивает проверку первыми N критериями (диагностический прогон, не
  настоящий балл). Судья `flash` дешевле и быстрее, `pro` строже.

## Границы и предостережения
- Не выдавать прогон по `criteria_limit` за официальный балл: в отчёте видно,
  сколько критериев проверено (`проверено N из M`).
- Не переписывать рубрику в деливерабл дословно ради PASS: судья оценивает
  содержание, но такой меморандум бесполезен как работа.
- Задания `firm-knowledge` ссылаются на общий корпус `dms/` (гигабайты) и почти
  не имеют локальных документов — для тренировки брать практики с материалами
  дела (`employment-labor`, `corporate-governance`, `litigation-*`).
- `diligence` содержит рубрики на 1114 критериев: полный прогон — сотни вызовов
  судьи. Начинать с `show`, потом решать.
