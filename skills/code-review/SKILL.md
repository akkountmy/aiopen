# Ревью кода

Проверяет диф по существу: корректность, безопасность, ошибки, состояние, контракты, тесты, производительность. Вкусовщина вливание не блокирует.

## Когда включать
- «сделай ревью», «посмотри код», «можно вливать?», «проверь перед мержем»;
- перед правкой `server.mjs`/`src/*.mjs` в `D:\DSHarness-0.1\DSH.OPEN.WEB` и деплоем бота `D:\DSHarness\telegram`;
- диф трогает сеть, авторизацию, файлы, данные пользователя.

## Процесс
1. Зафиксировать рамки: задача, диф, чем проверяется. Диф — текстом в запросе или `find_in_files` по изменённым файлам, файлы — `read_file`. Оболочки и `git` на сайте нет. Задача не названа — спросить.
2. Прочитать диф целиком до первого замечания.
3. Сверить с задачей: каждая строка обоснована как «задача требует именно её». «Заодно почистил» — просьба вынести в отдельный PR: раздутый диф прячет баг.
4. Пройти категории: корректность и крайние случаи; безопасность (валидация входа, права, инъекции, секреты); ошибки (что видит клиент, что идёт в лог); состояние и гонки (общий `Map`/кэш/файл, параллельные запросы); контракт API (форма ответа, старый клиент); тесты на исправленный баг; производительность (запрос в цикле, чтение файла целиком, синхронный `fs` в горячем пути, утечка таймеров). Затем чек-лист окружения ниже.
5. Severity. Блокер: уязвимость, потеря данных, гонка, ломается контракт API, критичный путь без обработки ошибок. Совет: нет валидации входа, непонятная логика, нет теста на важное, дублирование, узкое место. Придирка: стиль без линтера, имя, альтернатива.
6. Формат: `БЛОКЕР — безопасность: вход подставляется в запрос`, затем `server.mjs:142`, строка «почему» с конкретным сценарием, строка «как». Совет — просьбой: «стоит добавить…, потому что…». О коде, не о человеке: «здесь падает», а не «ты не подумал»; неясен замысел — вопрос, а не приговор: «`retry` тут намеренно без backoff?».
7. Всё одним списком за проход: дриблинг по одному комментарию растягивает работу. Отметить и сделанное хорошо, конкретно.

## Чек-лист окружения
Node ESM (`server.mjs`, `src/*.mjs`) и бот `D:\DSHarness\telegram`:
- [ ] `await` в обработчике обёрнут или ошибка уходит в `next(err)`/`.catch`;
- [ ] клиенту статус и текст, а не стек; нигде нет токенов, паролей, telegram token, пар ключей — только env или хранилище;
- [ ] у сетевых вызовов таймаут (`AbortSignal.timeout`): зависший запрос держит процесс;
- [ ] ретрай только идемпотентного или с ключом, с backoff и пределом; повтор не дублирует запись;
- [ ] состояние в памяти модуля не переживает перезапуск и не гоняется между запросами; `setInterval` очищается, интервал не копит параллельные запуски;
- [ ] пути не зависят от cwd (`import.meta.url`, `path.join`), запись атомарна (tmp + rename), нет доверия к `..`;
- [ ] ESM: `.mjs` в импортах, без `require` и `__dirname`; новая env с дефолтом.

## Минимальный диф
Переписать рабочий код «чище» в том же PR нельзя — только отдельным. Абстракция на трёх похожих строках не замечание (хелпер с четвёртого повтора). Защитный код для невозможного тоже: валидация нужна на границах. Замеченное вне задачи — в follow-up, не в блокеры.

## Чек-лист перед выдачей
- [ ] диф прочитан целиком; у каждого замечания файл:строка, severity, «почему», «как»;
- [ ] нет замечаний вида «плохо» / «надо улучшить»;
- [ ] секретов в дифе и логах нет (иначе блокер);
- [ ] есть тест на баг или сказано, как проверяли вручную;
- [ ] follow-up отдельно, всё выдано одним списком.

## Что отдать пользователю
Одно сообщение (или `REVIEW.md` с коротким именем): вердикт первой строкой — «вливать можно» / «нельзя: N блокеров» / «можно после исправлений»; что проверено; блокеры, затем советы; что сделано хорошо; follow-up вне рамок. Больше экрана — таблица: severity, файл:строка, проблема, что сделать.

## Анти-паттерны
- Стена замечаний без severity.
- Вкусовщина в блокерах при живом линтере.
- Требовать тесты на всё вместо важных путей.
- Расширять ревью до рефакторинга: «пока ты здесь, перепиши на async/await».
- Молчание про секреты, таймауты и ретраи в сетевом коде.
