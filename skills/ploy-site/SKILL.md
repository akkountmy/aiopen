# Сайты на Ploy: сборка, перенос, публикация

Ploy (https://ploy.ai) — платформа с ИИ-редактором и хостингом. Каждый сайт там это
проект **Astro 6 + React + TypeScript + Tailwind 4** на Cloudflare Workers; рядом
живут формы-коллектор, PloyDB (своя база), домены, вебхуки и постоянные задания.
Главное правило: Ploy не «переваривает любой репозиторий» — на его стартер код
переносят осознанно. Роль агента — локальный разработчик: аккаунт, сайты,
переменные и публикацию делает CLI, исходники — Git.

## Сначала про окружение

CLI Ploy есть только под **macOS и Linux** (`install.sh` проверяет `uname -s`;
сборки под Windows нет). В облачном контейнере этого приложения CLI тоже нет.
Рабочие пути:

1. **Веб-редактор ploy.ai** — работать в браузере, CLI не нужен.
2. **GitHub Code Sync** (платный тариф) — связать репозиторий и пушить обычным `git`.
3. **Linux-поверхность** (WSL, Docker, VPS, чужая машина) —
   `curl -fsSL https://ploy.ai/install.sh | sh`, затем `ploy login`.

Пока канала нет, агент всё равно готовит проект целиком локально (структура,
страницы, стили, контент), а публикацию оставляет человеку. Если `ploy.ai` не
открывается — сначала навык `obscura`.

## Рабочий процесс

1. **Оценить состояние**: есть ли привязанный checkout (`ploy.site`,
   `ploy.workspace`, `ploy.apiurl` в Git-конфиге). Если есть — это правка, а не
   миграция. Зафиксировать исходный коммит и незакоммиченные изменения.
2. **Выбрать объём**: весь сайт или страницы; какие серверные зависимости надо
   заменить (API, формы, авторизация, картинки, cron).
3. **Создать назначение**: `ploy login` → `ploy workspace list` →
   `ploy workspace use --id <id>` → новый сайт из стартера либо
   `ploy site init --from <path> --wait --json` для совместимого дерева. Для нового
   сайта сразу читать `AGENTS.md` в корне — там конвенции проекта.
4. **Проверить сборку** в назначении: `npm run verify`, затем
   `npx wrangler deploy --dry-run` (после сборки, не удаляя `dist`), затем
   `npm run preview` и обход всех маршрутов.
5. **Синхронизировать и опубликовать**: `git push ployspace HEAD:main` →
   `ploy site git sync --json` → дождаться рестарта превью и проверить его →
   `ploy site publish --wait` только если публикацию просили.

## Структура стартера (важно для дизайна)

| Что | Где | Правило |
|---|---|---|
| Маршруты | `src/pages/*.astro` | тонкая страница + общий layout; URL без групп роутов |
| Каркас, метаданные, JSON-LD | Astro-layout | canonical, соцкарточки, noindex — здесь |
| Интерактив | React-острова `client:*` | `"use client"` не гидратирует Astro; контекст не живёт между островами |
| Контент | `src/content.config.ts` | коллекции явно; слаги сохранять |
| Стили | Tailwind 4 в стартере | конфиг Tailwind 3 переносится вручную (grid-треки через пробел или `_`) |
| Статика | `public/` | платформенные `public/_headers` и `.assetsignore` не трогать |
| Лок-файл | `bun.lock` | канонический; `package-lock.json` стартер удаляет после первого sync |
| Пакет | имя `ploy-web` | скрипты `verify` / `preview` не переименовывать |

React может упасть при рендере, а сборка при этом завершится с кодом 0 и пустым
HTML — проверять не код ответа, а наличие заголовков и текста на странице.

## Перенос существующего сайта

**Next.js (App Router).** Маршрут → `src/pages/<slug>.astro` + общий layout;
`next/link` → `<a>` (Astro сам делает переходы быстрыми); `next/image` → Astro
image или `<img>` с `width`/`height`; `next/font` → локальные шрифты в `public/`
или `@font-face`; клиентские хуки/состояние → React-остров с `client:load` или
`client:visible`; route handler → Astro endpoint, совместимый с Workers;
`next.config` redirects → Astro redirects (указывать 308 явно);
`NEXT_PUBLIC_*` → `PUBLIC_*` только для того, что действительно публично.
Server Actions, ISR, middleware, `next/dynamic` — переписывать, не имитировать.

**Vite / клиентский React.** Собрать разметку в один общий остров или разбить по
секциям; проверить гидрацию (невалидная вложенность DOM ломает её молча —
проверять консоль превью); Tailwind 3 → 4; ассеты из `src/assets` переносить в
`public/` или импортировать через `astro:assets`.

**Nuxt / SvelteKit.** Дизайн и поведение берём как входные данные и реализуем
заново на Astro: `useFetch`/`load` → `getStaticPaths` и фронтовый `fetch` к
публичному API; серверные роуты и image-API заменяем на Workers-путь; слоты и
`<script setup>` переписываются в React-острова.

**Обычный Astro или статика.** Проверить только версии (`astro`, `@astrojs/*`,
Node 20+), структуру контент-коллекций, что нет чужих адаптеров и своего
`vite.config` с плагинами, которых нет в стартере; затем `ploy site init --from`.

**Общее для любого переноса.** Слаги и редиректы сохранять один в один (иначе
потеряются позиции в поиске); canonical и sitemap — через layout; формы
переводить на формы Ploy, а не на сторонний сервис; шрифты и картинки — локально;
внешние CDN-скрипты убирать; env-переменные — `ploy variable` / `ploy secret`;
базу — PloyDB; cron — постоянные задания Ploy; права и куки — заново, чужие
сессии не переносятся.

**Никогда не копировать**: `.env`, секреты, историю Git, `node_modules`, `.next`,
`dist`, кэши, пользовательские загрузки, лицензионные шрифты без прав.

## Перенос сайта между воркспейсами

Нужны CLI ≥ 0.12.0, права admin/owner в обоих воркспейсах и браузерный
`ploy login`. Порядок: выбрать источник и назначение (`ploy workspace list`,
`ploy workspace use`), убедиться, что в назначении хватает места и тарифа;
перенести код (`ploy site git clone`, затем push в `ployspace` назначения или
Code Sync), перенести базу PloyDB (схема, затем данные, затем проверка счётчиков),
перенести ассеты и шрифты, перенастроить формы и вебхуки (URL меняются),
перевесить домен в самом конце, проверить превью и публикацию, и только после
успешной проверки удалять исходный сайт. Пока перенос не подтверждён, источник
не удаляется: откат возможен только пока он жив.

## Проверки, без которых нельзя говорить «готово»

- `npm run verify` на текущем HEAD, в том числе после ребейза на `ployspace/main`.
- `npx wrangler deploy --dry-run` упаковывает воркер (это проверка, не деплой).
- Превью открыто и отрисовано: маршруты, мобильное меню, формы, 404, редиректы,
  метаданные, шрифты, ассеты, поиск.
- `ploy site git sync` со статусом `preview: restarting` — это «принято», а не
  «страница жива»: превью проверяется отдельно.
- Публикация: сверить воркспейс и сайт (`ploy site list`), выполнить
  `ploy site publish --wait`, открыть живой URL. Ни сборка, ни sync публикацией
  не считаются.

## Никогда

Force-push в `ployspace`; пересоздание сайта ради обхода упавшей проверки;
приватные API вместо неподдержанной команды; вывод токенов и переменных
в отчёт; удаление исходного сайта до подтверждённого переноса.
