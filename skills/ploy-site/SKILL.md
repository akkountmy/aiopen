# Сайты на Ploy: сборка, перенос, публикация

Ploy (https://ploy.ai) — хостинг-платформа с ИИ-редактором. Каждый сайт там это
проект **Astro 6 + React + TypeScript + Tailwind 4** на Cloudflare Workers; рядом
живут формы-коллектор, PloyDB (своя база), домены и вебхуки. Отсюда главное
правило: Ploy не «переваривает любой репозиторий» — на его стартер переносят код
осознанно, а не подключают чужой фреймворк.

Роль агента — локальный разработчик: аккаунт, сайты, переменные и публикацию
делает CLI, исходники — Git.

## Сначала про окружение

CLI Ploy существует только под **macOS и Linux** (`install.sh` проверяет
`uname -s`; сборки под Windows нет). В облачном контейнере этого приложения CLI
тоже не установлен и ставить его туда не нужно — отсюда есть три рабочих пути:

1. **Веб-редактор ploy.ai** — открыть сайт в браузере и работать там, CLI не нужен.
2. **GitHub Code Sync** (платный тариф Ploy) — связать репозиторий и пушить
   обычным `git`; синкает сам Ploy.
3. **Linux-поверхность** (WSL, Docker, VPS, локальная машина) — там ставится
   `curl -fsSL https://ploy.ai/install.sh | sh` и работает `ploy login`.

Если сеть до `ploy.ai` медленная или страница не открывается — сначала навык
`obscura`, затем повтор. Пока канала нет, агент всё равно готовит проект целиком
локально (структура, страницы, стили, контент), а публикацию оставляет человеку.

## Рабочий процесс

1. **Оценить состояние**: есть ли уже привязанный checkout (`ploy.site`,
   `ploy.workspace`, `ploy.apiurl` в Git-конфиге) — тогда это обычная правка, а не
   миграция. Зафиксировать исходный коммит и незакоммиченные правки.
2. **Выбрать объём**: весь сайт или выбранные страницы; какие серверные
   зависимости придётся заменить (API, формы, авторизация, картинки, cron).
3. **Создать назначение**: `ploy login` → `ploy workspace list` →
   `ploy workspace use --id <id>` → новый сайт из стартера либо
   `ploy site init --from <path> --wait --json` для уже совместимого дерева.
   Для нового сайта сразу читать `AGENTS.md` в корне — там конвенции проекта.
4. **Проверить сборку** в назначении: `npm run verify`, затем
   `npx wrangler deploy --dry-run` (после сборки, не удаляя `dist`), затем
   `npm run preview` и обход всех маршрутов руками.
5. **Синхронизировать и опубликовать**:
   `git push ployspace HEAD:main` → `ploy site git sync --json` → дождаться
   рестарта превью и проверить его → `ploy site publish --wait` только если
   публикацию просили явно.

## Где что лежит в стартере (важно для дизайна)

| Что | Где | Правило |
|---|---|---|
| Маршруты | `src/pages/*.astro` | тонкая страница + общий layout; URL без групп роутов |
| Каркас, метаданные, JSON-LD | Astro-layout | canonical, соцкарточки, noindex — здесь |
| Интерактив | React-острова с `client:*` | `"use client"` не гидратирует Astro; контекст не живёт между островами |
| Контент | `src/content.config.ts` | коллекции явно; слаги сохранять |
| Стили | Tailwind 4 в стартере | Tailwind 3 конфиг переносится вручную (grid-треки через пробел/`_`) |
| Статика | `public/` | не трогать платформенные `public/_headers` и `.assetsignore` |
| Лок-файл | `bun.lock` | канонический; `package-lock.json` стартер удаляет после первого sync |
| Пакет | имя `ploy-web` | скрипты `verify` / `preview` не переименовывать |

Осторожно: React может упасть при рендере, а сборка при этом завершится с кодом 0
и пустым HTML — проверять не код ответа, а наличие заголовков и текста.

## Перенос существующего сайта

Полная процедура, карта соответствий фреймворков (Next.js, Vite/React, Nuxt,
SvelteKit, обычный Astro) и правила проверки — в
[references/migration.md](references/migration.md). Коротко:

- **Next.js**: App Router → `src/pages/*.astro` + layout; `next/link` → `<a>`;
  `next/image` → Astro image или `<img>` с размерами; `next/font` → локальные
  шрифты; хуки/состояние → React-остров; route handler → Astro endpoint,
  совместимый с Workers; `next.config` redirects → Astro redirects (308 явно),
  `NEXT_PUBLIC_*` → осознанно `PUBLIC_*`.
- **Vite / client-only React**: собрать компоненты в один общий остров, проверить
  гидрацию (невалидная вложенность DOM ломает её молча), Tailwind 3 → 4.
- **Nuxt / SvelteKit**: дизайн и поведение берём как входные данные и
  реализуем на Astro; серверные роуты и image-API заменяем на Workers-путь.
- **Никогда**: не копировать `.env`, секреты, историю Git, `node_modules`,
  `.next`; переменные — через `ploy variable` / `ploy secret` / `ploy env`.

Перенос сайта **между воркспейсами** (код, база, ассеты, формы, домен, затем
удаление источника) — отдельная процедура:
[references/workspace-transfer.md](references/workspace-transfer.md). Требует
CLI 0.12.0+, права admin/owner в обоих воркспейсах и браузерный `ploy login`.

## Проверки, без которых нельзя говорить «готово»

- `npm run verify` на текущем HEAD, в том числе после ребейза на `ployspace/main`.
- `npx wrangler deploy --dry-run` упаковывает воркер (это проверка, не деплой).
- Превью открыто и отрисовано: маршруты, мобильное меню, формы, 404, редиректы,
  метаданные, шрифты, ассеты, поиск.
- `ploy site git sync` со статусом `preview: restarting` — это «принято», а не
  «страница жива»: превью проверяется отдельно.
- Публикация: сверить воркспейс и сайт (`ploy site list`), выполнить
  `ploy site publish --wait`, открыть живой URL. Ни сборка, ни sync сами по себе
  публикацией не считаются.

Никогда: force-push в `ployspace`, пересоздание сайта ради обхода проверки,
приватные API вместо неподдержанной команды, вывод токенов в отчёт.
