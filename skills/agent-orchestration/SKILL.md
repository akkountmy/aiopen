# Оркестрация субагентов

Роль: разложить работу на части, отдать субагентам самодостаточные задания и свести ответы в проверенный результат. Оркестратор не делает работу сам: делит, делегирует, сверяет.

## Когда включать

- «сделай параллельно», «разбей на части», «раздай подзадачи», «долго, разложи».
- Части независимы или требуют разного контекста (поиск vs правка кода).
- Нужен независимый взгляд: ревью, проверка цифр, аудит.

## Процесс

1. **Проверь, нужна ли декомпозиция.** По умолчанию одна задача — один агент. Дробить, только если части независимы, контексты разные, объём больше 3–4 файлов или проверяющий должен быть не-автором. Не дробить: шаг 2 потребляет результат шага 1 в процессе, декомпозиция неизвестна заранее, передача контекста дороже выигрыша. Не можешь назвать части и их границы — не дроби.

2. **Дели по артефактам, а не по шагам.** У каждого файла ровно один писатель. Общие файлы (`package.json`, lock, `index`-баррели, конфиги, миграции) правит только оркестратор. До fan-out зафиксируй контракты: имена функций, схему JSON, формат таблицы — иначе части не сойдутся. В параллели нет общего изменяемого состояния.

3. **Пиши самодостаточный промпт.** `spawn_agent` не видит ни переписку, ни файлы, которые ты не передал: задача, входы с путями, границы и способ проверки — всё в промпте. У сайта субагент одного типа: глубина 1, до 4 задач параллельно. «Как мы обсуждали» не работает.

```
ЗАДАЧА: <что должно появиться на выходе>
ВХОД: <файлы с путями, что читать первым>
СДЕЛАТЬ: <нумерованные шаги>
ГРАНИЦА: не трогать <файлы>; не менять <контракты>; не ставить зависимости
ПРОВЕРКА: <команда или способ>
ОТВЕТ: статус / изменённые файлы / как проверял / риски / уверенность
```

Требуй структуру, а не прозу. Одна роль — одна когнитивная задача: «исследуй, напиши, оцени» — это два-три агента.

4. **Запускай.** Инструмент один — `spawn_agent`: он запускается в фоне и возвращает id, результат забираешь, когда он нужен; ждать его внутри своего хода нельзя. Параллельно 2–4 задачи (предел 4 на вызов, глубина 1: субагент не запускает своих). «Фаз» у сайта нет — фазы задавай сам, порядком вызовов и журналом. Иерархия «оркестратор → субагенты», не mesh.

5. **Собери.** Журнал — файлом через `write_file`: кому отдано, статус, где результат. Крупные результаты — в файлы, в контекст выжимку.

6. **Сверь.** Не верь «готово»: перечитай изменённые файлы, запусти проверку сам. Противоречия не усредняй — разрешай по доказательству и записывай основание. Двое правили один файл — дифф, одна версия, виновника перезапустить с владельцем.

7. **Падение.** Повтор запуска до 2 раз, задача — до 3 попыток, каждая с новым фидбеком. Замены: сузить задачу → сделать самому урезанно → к пользователю. Реши заранее: все / часть / ноль результатов. Не сделанное — в отчёт.

8. **Схема: исследование → разработка → ревью → приёмка.**

```
1 исследование  subagent (только чтение) → research.md со ссылками
2 разработка    subagent по промпту + research.md → код
3 ревью         отдельный subagent, критерии иначе → PASS/FAIL + правки
4 приёмка       оркестратор сам читает файлы и проверяет
                FAIL → шаг 2 (до 3 раз), дальше — к пользователю
```

Ревьюер — не автор: критерии у него сформулированы иначе.

## Чек-лист перед выдачей

- [ ] Один писатель на файл; контракты зафиксированы до fan-out.
- [ ] По каждой ветке известно: выполнено / частично / провалено.
- [ ] Проверку запускал сам, а не по отчёту агента.
- [ ] Не сделанное перечислено с причиной.

## Что отдать пользователю

Свод: что сделано и какими ролями, файлы с путями, чем проверено, что не сделано и почему, риски. Для длинной работы — таблица «ветка / агент / статус / результат / проверка».

## Анти-паттерны

- Дробить всё подряд: координация дороже работы.
- Ждать, что субагент догадается по контексту, которого не видит.
- Параллелить писателей в один файл — гонка и потерянные правки.
- Пускать автора проверять себя и называть это ревью.
- «Всё готово» без собственной проверки артефактов.
